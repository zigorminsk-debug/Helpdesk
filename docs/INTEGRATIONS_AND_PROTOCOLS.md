# Интеграции, API и сетевые протоколы Help-CSL

В этом документе описаны все внешние и внутренние протоколы взаимодействия **Help-CSL** и критические нюансы корпоративной инфраструктуры `csl.by`.

---

## 1. Jira Server / Data Center (REST API v2) и Jira Cloud (REST API v3)

Основной файл: `app/src/main/java/com/helpdesk/jiraagent/data/JiraApiClient.kt` + `JiraJsonParser.kt`.

### 1.1. Поддерживаемые способы авторизации
- **`AuthType.BASIC`** — классический `Authorization: Basic base64(login:password)` для корпоративных Jira Server / Data Center;
- **`AuthType.PAT_BEARER`** — `Authorization: Bearer <Personal Access Token>` для Jira Data Center 8.14+;
- **`AuthType.CLOUD_TOKEN`** — `Basic base64(email:api_token)` для облака Atlassian (`*.atlassian.net`).

### 1.2. Особенности русской локали Jira и стратегия JQL-выборки
1. **Запрет строкового `statusCategory = Done` в JQL**:
   - На серверах Jira Server/DC с русским языком интерфейса запрос `statusCategory = Done` или `statusCategory != Done` падает с **HTTP 400** (`The value 'Done' does not exist for the field 'statusCategory'`).
   - **Решение в `JiraApiClient`**: клиент запрашивает справочник `/rest/api/2/status`, группирует числовые `id` статусов по машинному ключу `statusCategory.key` (`"new"`, `"indeterminate"`, `"done"`), кэширует их и строит JQL через числовые ID (`status in (3, 10001, ...)`), `statusCategory = 3` / `statusCategory != 3` или `resolution is EMPTY` с каскадным fallback.
2. **Защита от «затопления» очереди алертами Zabbix / Backup**:
   - Если запрашивать только последние `N` задач по `ORDER BY updated DESC`, сотни автоматических тикетов мониторинга вытесняют реальные открытые заявки клиентов и тикеты в статусе «В работе».
   - Поэтому `fetchTickets()` выполняет целевую подгрузку:
     - свежей общей ленты проекта;
     - всех незакрытых заявок в статусах `IN_PROGRESS` (`indeterminate`);
     - живых клиентских обращений портала JSM (отсекая технических авторов `zabbix`, `monitoring` и т.п.), а затем дедуплицирует их по `key`.
3. **Внутренние заметки JSM (`🔒 Внутренняя заметка`)**:
   - При включённом флаге `internalOnly = true` в `POST /rest/api/2/issue/{key}/comment` передаётся свойство `properties = [{"key": "sd.public.comment", "value": {"internal": true}}]`, чтобы комментарий был скрыт от клиента на портале Jira Service Management.

## 2. Командная синхронизация через служебные комнаты Jira

Поскольку у Help-CSL нет отдельного проприетарного сервера, общая командная информация между всеми ПК и смартфонами инженеров хранится в специальных служебных задачах Jira (автоматически скрываемых из рабочих очередей):

| Подсистема | Маркер служебной задачи в Jira | Кодек сериализации |
|---|---|---|
| Мастерская **«В ремонт»** (`REM-1001+`) и справочник клиентов | `[HELPCSL_REPAIR_REGISTRY_ROOM]` | `RepairEquipmentCodec` + `ClientDirectoryCodec` (`RepairEquipment.kt`) |
| Внутренний **«Чат»** смены + закреплённая заметка смены | `HELPCSL_ADMIN_CHAT_ROOM` | `AdminChatCodec` (`AdminChatMessage.kt`) |
| Облачный **«🏢 Техпаспорт клиента»** | `[HELPCSL_CLIENT_PASSPORTS_ROOM]` / вложения и комментарии комнаты | `ClientTechPassportCodec` (`ClientTechPassport.kt`) |

Все операции записи выполняют чтение актуального состояния перед записью (merge по `id` и `updatedAtMillis`), благодаря чему правки разных инженеров не затирают друг друга, а удаление карточек ремонта сохраняется как мягкое удаление (`isDeleted = true` с ФИО, датой и причиной во вкладке «🗑 Удалённые»).

## 3. Confluence Wiki (`https://w.csl.by`) и полная офлайн-база

Основные файлы: `ConfluenceWikiClient.kt` и `ConfluenceOfflineStore.kt`.

1. **Единый вход с Jira и поддержка 2FA**:
   - По умолчанию используются те же логин и пароль/токен, что и для Jira (`effectiveWikiLogin`, `effectiveWikiPassword`).
   - Для Confluence Server/DC поддерживаются: `Bearer PAT`, сессионный вход через `/dologin.action` и перенос авторизованных `Cookie` из встроенного `WebView` (если на сервере включена двухфакторная аутентификация).
   - **Важно:** для проверки доступа используется `/rest/api/space?limit=1` (и HTML fallback), так как `/rest/api/user/current` существует только в Confluence Cloud и на `w.csl.by` отдаёт `404`.
2. **Нативное чтение и алфавитный справочник**:
   - Пространства (`Spaces`), дерево дочерних страниц, алфавитная группировка клиентов (`А–Я`, `A–Z`, `0–9`), парсинг Confluence Storage XHTML (таблицы с копированием ячеек по клику, блоки кода, информационные панели и изображения).
3. **Полная офлайн-база и защита данных при увольнении**:
   - Раз в сутки (а также вручную по кнопке с прогресс-баром) `ConfluenceOfflineStore` скачивает дерево страниц в локальное хранилище для мгновенной работы без интернета.
   - Если сервер Jira или Confluence возвращает `401 / 403` с признаком деактивированной учётной записи сотрудника, локальная офлайн-база и кэш автоматически очищаются (`wipeLocalSecurityData`).

## 4. Мониторинг Zabbix (`https://z.csl.by`)

Основные файлы: `ZabbixApiClient.kt` и `ZabbixModels.kt`.

1. **Совместимость JSON-RPC (Zabbix 5.x / 6.x / 7.x)**:
   - Сначала вызывается `apiinfo.version` **строго без заголовка `Authorization` и без поля `auth`** (в Zabbix 6.4+ передача `auth` в `apiinfo.version` вызывает ошибку протокола).
   - В зависимости от версии сервера `user.login` автоматически выбирает параметр `username` (Zabbix 5.4+) или `user` (старые версии), а дальнейшие запросы используют `Bearer`-заголовок (Zabbix 6.4+/7.x) или поле `"auth"` в JSON.
2. **Политика оповещений (строго `Disaster = 5`)**:
   - По умолчанию `DEFAULT_ZABBIX_MIN_SEVERITY = 5`: звуковая сирена и всплывающий баннер срабатывают **только на аварии уровня `Disaster (5)`**.
   - Поддерживаются три режима работы со списком проблем:
     - **Подтвердить (`Ack`)** — отправляет `event.acknowledge` с комментарием инженера прямо на сервер Zabbix;
     - **Скрыть текущую проблему (`✕`)** — убирает уже известную карточку из активной ленты в раздел «🔕 Скрытые», чтобы видеть только вновь возникающие сбои;
     - **Заглушить триггер навсегда (`🔇`)** — добавляет `ZabbixMutedRule` по `objectId` / имени триггера для нерешаемых или чужих триггеров.

## 5. Сетевая устойчивость (`OkHttp`) и корпоративный SSL/TLS

- Клиенты `JiraApiClient` и `ZabbixApiClient` используют **раздельные пулы соединений `OkHttpClient`** с включённым `pingInterval` для HTTP/2 и автоматическим пересозданием сокетов при переключении сети (`Wi-Fi ↔ мобильная сеть` на смартфоне или просыпании ноутбука).
- При включённой опции `trustSelfSignedSsl = true` настраивается кастомный `X509TrustManager` для работы во внутренних корпоративных сетях и VPN с собственным УЦ.

## 6. Перенос настроек по зашифрованному QR-коду (`HELPCSL1:`)

Основные файлы: `SettingsTransferCodec.kt` (Android) и `DesktopStorage.kt` (Windows).

- Формат строки: `HELPCSL1:<Base64Url(Salt[16] + IV[12] + Ciphertext_GCM)>`.
- Полезная нагрузка сжимается `GZIP` и шифруется `AES-256-GCM` с ключом `PBKDF2WithHmacSHA256` (с поддержкой пользовательского одноразового PIN-кода).
- По умолчанию личный пароль/токен исключается из QR-пакета (передаются URL серверов, правила фильтрации, график РБ и шаблоны), но при настройке собственного второго устройства инженер может включить передачу полного профиля в 1 скан.
